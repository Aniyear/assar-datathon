## Шаг 1 — сеть и запуск без ожидания ML

Пока Омар завершает ML своим методом оценки:

- Передай ему локальный доступ к результатам уже завершённого сравнения. Не отправляй наблюдения облачным агентам. Получи от него только агрегаты и выбор модели.
- Проверь фактический HEAD интеграции, пути к весам/runtime и рабочее окружение. Ничего не скачивай повторно без необходимости.
- Выбери и практически подготовь способ публичного HTTPS-доступа к твоему сервису: доступный управляемый сервер/reverse proxy/туннель. Не привязывай план к несуществующему домену. Выясни необходимость аккаунта, доступов и внешнего порта сейчас, а не после финального ML.
- Убедись, что передача данных идёт только к разрешённому сервису команды, без внешнего AI/inference, хранения и аналитики стороннего приложения. За внешним HTTP-адресом GPU остаётся локальным. Условия инфраструктуры должны соответствовать кейсу.
- Локально проверь frontend/HTTP со штатными синтетическими fixtures. Если поднимаешь внешнюю техническую страницу до готовности ядра, явно обозначь её тестовой: она не считается сдаваемым сервисом.
- Практическое изменение публичного доступа выполнить как отдельный явный шаг под твоим контролем. Если инструмент требует конкретного действия человека, агент сообщает его сразу. Доступ для жюри не оставлять только в виде Markdown-инструкции.

Сохранение model API на `127.0.0.1` обязательно. Публикуется продуктовый HTTP API, не порт llama-server. Ключ — вне Git, URL и клиентского JS. Проверка HTTPS без отключения проверки сертификата.

## Шаг 2 — довести техническую часть, пока Омар пишет ядро

Порядок важности:

1. Надёжный запуск по одной инструкции, правильные пути, один владелец GPU и один сервер модели.
2. Реальные загрузка/polling/ошибки и соответствие внешнему контракту.
3. Сохранение результата после очистки временных файлов и перезапуска.
4. Внешний доступ, отсутствие сна/смены адреса во время проверки, понятная остановка и резервная копия.
5. Только затем косметика интерфейса.

В UI достаточно понятной загрузки, времени ожидания, вердикта, карточек событий/кадров, видеоплеера и сообщения об ошибке. Не нужны новые экраны, идеальная анимация и новый CSS-фреймворк. Дизайн Argon применять только поверх проверенной логики; не заменять весь app.js старым ответом Gemini.

## Шаг 3 — принять точный ML-handoff

Омар должен передать:

- ML-коммит и base, точные импорты/сигнатуры.
- Выбранные GGUF/mmproj/runtime с revision/SHA256, параметры и версию промпта.
- Реализованный тип, условия и контрпримеры, нормативный источник, причины применимости.
- Dev-агрегаты, долю failed, время/память, известные ошибки.
- Конкретные изменения общих файлов и команду запуска.

Проверь только необходимые интеграционные вещи, не начинай новый исследовательский цикл. Внеси принятые настройки в `configs/model.yaml` и правила в `app/rules/catalog.json`. Статус verified должен отражать подтверждённый источник/применимость и реализованные условия, а не желание пройти startup.

Если общий тип нужно расширить, сделай одно согласованное изменение с потребителями. Внешний API жюри сохраняется. Ошибка → failed; не добавляй публичный третий verdict и не превращай failed в no_violation.

Readiness-флаги выставлять по фактическим проверкам нужной комбинации code/config/model/catalog. Технический smoke старой 2B не делает новый 4B-кандидат автоматически проверенным. Для первых измерений используй явный validation-entrypoint; после подтверждения запускается обычный production-entrypoint. Не создавай круг «для теста нужен ready, для ready нужен тест».

## Шаг 4 — реальный первый проход после handoff и согласования GPU

Используй существующие `docs/MVP_LAUNCH.md` и `docs/MVP_ACCEPTANCE.md`, обновив точные пути/версию по handoff. Не исполняй их как будто все предусловия уже выполнены.

Сначала два заранее выбранных dev-ролика по поддерживаемому покрытию:

1. Upload через реальный UI/API с правильным ключом.
2. Processing → настоящий done с ожидаемым результатом, а не ответ фикстуры.
3. Для violation — корректные таймкоды и 1–3 исходных JPEG; Омар локально подтверждает смысл.
4. Для no_violation — пустой список. Отрицательный результат оценить по выбранному покрытию, не объявлять универсальным доказательством.
5. Измерить полный путь upload → terminal response. Технические и содержательные неудачи записать, не подбирать новый ролик до красивого PASS.

Если этот этап не проходит, передать ровно дефект владельцу: смысл — Омару, API/процесс/путь — себе. Не отправлять всем агентам широкое «ещё улучшить». После исправления повторить затронутый сценарий.

## Шаг 5 — приёмка и фиксация

- Заморозить code/config/catalog/weights. После этого обычные улучшения прекращаются.
- На фиксированном наборе получить распределение вердиктов, ошибки и failed. Считать долю failed от всех входных роликов; не маскировать её условной точностью только успешных ответов.
- Проверить самый длинный dev-ролик по полному времени ≤300 с, повторный POST и устойчивое чтение результата после очистки/штатного перезапуска.
- После фиксации версии выполнить закрытую оценку, не передавая её сцены в ML-подбор. Если из-за времени проверена не вся часть, явно указать размер и принцип выбора. Десять роликов не дают высокой статистической уверенности. После настройки по test он перестаёт быть независимым.
- Выполнить запрос с другой сети, например с управляемого командой устройства через мобильный интернет: UI, неверный ключ, правильный ключ, реальный результат. Не использовать облачный AI-браузер для просмотра банковских кадров.
- Подтвердить отсутствие внешних AI-запросов и доступность локальных ресурсов. Отсутствие интернета для inference и внешний HTTPS-доступ проверяются раздельно, а не взаимоисключающей настройкой.
- Сохранить release commit, версии/лицензии, инструкцию и квитанцию. Ключ передаётся капитану отдельно. Базу результатов копировать штатно, не теряя WAL работающей SQLite.

Публичная публикация и отправка жюри — два разных действия. Сначала Анияр проверяет сервис, затем капитан передаёт адреса/ключ по установленному каналу.
