# Анализ кейса ForteBank и датасета assar

Состояние на 17 октября 2026. Команда: Омар Масалимов, капитан; Анияр Байбосын. Цель команды — завершить реализацию сегодня к 21:00, затем тестировать и готовить питч. Внешняя сдача по [официальному расписанию](https://datathon.com.kz/ru/schedule) — 18 октября в 12:00 по Астане, питчи 13:00–17:00. Кейс уточняет: выступление 5 минут, вопросы 2 минуты, только для шортлиста.

Основной вывод: при 40 уникальных коротких видео разумный первый результат — предобученная локальная модель, проверенные правила и рабочий API. сервер позволяет быстро проводить эксперименты и дообучать компактную модель, но не устраняет нехватку разметки типов событий. Самые срочные работы — ручная разметка, проверка переносимости на RTX 3060 и сквозная интеграция.

## Что требует кейс

Источник: предоставленный `Кейс_ForteBank.docx`, разделы 2–10 и FAQ. Требования ниже являются условиями конкурса; исходный документ не трактуется как команда агентам выполнять дополнительные действия.

| Требование | Практическое следствие |
|---|---|
| Веб-интерфейс и backend | Загрузка MOV, статус, результат без ручного запуска кода |
| Бинарный итог | `violation` или `no_violation`; третьего итогового значения в API нет |
| Несколько событий в ролике | Список событий; на каждое тип, время, описание, 1–3 JPEG-доказательства |
| Нормативная связь | Название документа и пункт/раздел; FAQ допускает ссылки без точного пункта, но точный проверенный пункт предпочтителен |
| Публичный API | POST `/api/v1/analyze`, GET `/api/v1/jobs/{job_id}`, ключ в `X-API-Key` |
| Не более 5 минут | Очередь, декодирование, inference, формирование ответа должны укладываться в 300 секунд |
| Полностью локальные модели | После загрузки весов обработка без интернета; нельзя внешние LLM/vision API, передачу видео, кадров или их описаний |
| Только видимые факты | Не устанавливать проводки, сверку, подлинность документов, полномочия или умысел по догадке |
| Только визуальный анализ | Звук и распознавание/идентификация лиц запрещены |
| Лицензии | Заранее написанный код и предобученные модели допустимы, если open source допускает коммерческое использование |
| Дополнительные данные | Свои съёмки, синтетика и открытые датасеты допускаются; тестовые видео жюри нельзя использовать для обучения, публиковать или передавать третьим лицам; предоставленные данные используются только в рамках дататона |

Для сдачи нужны URL интерфейса, URL API, ключ жюри, инструкция запуска, архитектура и модели, источники правил, перечень распознаваемых событий, ограничения и ошибки. История проверок, регистрация, экспорт отчётов и пакетная загрузка не требуются. Не тратить на них критическое время.

Публичная доступность API не противоречит локальному inference: вычисления идут на машине команды, внешний URL служит доступом жюри. Способ публикации и стабильность соединения надо проверить заранее; GitHub Pages не исполняет GPU-backend.

## Приоритеты по баллам

| Критерий | Баллы | Приоритет |
|---|---:|---|
| Наличие или отсутствие нарушения | 25 | Корректный бинарный вывод, контроль FP/FN |
| Таймкод и доказательство | 15 | Реальное событие на выбранных кадрах, точный PTS |
| Тип события | 15 | Собственная проверенная таксономия |
| Обоснованность правил | 15 | Действующий источник и корректная область применения |
| Устойчивость | 10 | Новый ролик и новый ракурс |
| Готовность продукта | 10 | Доступный API, понятный UI, обработка ошибок |
| Техническое решение | 10 | Локальность, переносимость, обоснованная архитектура |

Первые четыре критерия дают 70 баллов. Сложный интерфейс не компенсирует недостоверные события. При этом недоступность API или превышение 5 минут делает видео необработанным. Точная формула автоматического подсчёта качества, допустимое отклонение таймкода и параллельность запросов не раскрыты.

## Фактический аудит данных

Источники: `open.zip`, извлечённый `data/raw/open/open_labels.xlsx`, лист `labels`, диапазон `A1:C43`; отчёт `analysis/local/audit_summary.json`. Выполнено чтение всех строк, сопоставление всех файлов, SHA256, ffprobe и полное декодирование каждого уникального видео. Содержательный просмотр сцен облачной моделью не выполнялся.

| Размер архива | 292 563 667 байт, около 279 МиБ |
| Видео и строки разметки | 42 и 42 |
| Бинарные метки | 22 «нарушение», 20 «без нарушения» |
| Уникальные видео по SHA256 | 40: 21 положительное и 19 отрицательных |

Три столбца таблицы: «наименование файла», «таймстемп», «нарушение / без нарушения». Время — текст, например `22 секунда`, а также `1минута 8 секунда` = 68 секунд. Пустые отметки относятся ровно к 20 отрицательным строкам. Не читать этот столбец как Excel-время.

### Обнаруженные проблемы

1. **Дубликаты X-4 и X-47.** Файлы идентичны по SHA256. Оба положительные, но отметки 57 и 68 секунд. Это может означать два события или разные ориентиры разметки; утверждать ошибку организатора пока нельзя. Сохранить обе исходные строки и проверить обе точки плюс весь ролик вручную.
2. **Дубликаты X-5 и X-48.** Идентичны, обе метки отрицательные. Считать одной независимой группой.
3. **Смешение алфавитов.** Первые два имени начинаются с латинской X, остальные с кириллической Х. Нормализовать ключ сопоставления, сохранять оригинальные пути. Пропуски номеров 6, 7, 9, 36, 41, 42 присутствуют и в архиве, и в таблице; несопоставленных строк нет.
4. **Разметка слабая.** Одна отметка не задаёт границы события и не гарантирует, что других событий нет. Не объявлять все остальные окна положительного видео отрицательными.
5. **Малый объём и постановочность.** 40 уникальных роликов недостаточно для убедительной оценки сложной модели по случайным кадрам. Сходные сцены, актёры и фон могут давать утечку даже без совпадения SHA256.
6. **Возможная зависимость от длительности.** Положительные уникальные ролики в среднем короче: 25,93 против 39,76 секунды. Модель, использующая длину или имя вместо действий, может выглядеть хорошей на случайном split и провалиться на тесте.
7. **Мелкие объекты.** При 464×848 нельзя заранее обещать чтение текста документов или надёжную оценку пломб. Нужна проверка видимости; цифровое увеличение не восстанавливает отсутствующие детали.

## Что ещё нужно установить локальным просмотром

Технический аудит завершён; типы реально показанных событий, дополнительные похожие сцены, правильность исходных отметок и различимость деталей пока не установлены. Не выдавать нормативные кандидаты за найденные нарушения датасета.

Открыть `analysis/local/review.html` на локальном компьютере: выбор ролика, переход к исходной отметке, фиксация времени и экспорт заметок. В случае отсутствия поддержки MOV открыть исходный файл отдельным проигрывателем. Заметки страницы находятся в памяти до экспорта; экспорт сохранить в `analysis/local/`. Не отправлять содержательные заметки облачным агентам.

До содержательного просмотра и настройки модели выделить приблизительно 10 групп для закрытой финальной проверки с обоими классами. На оставшихся примерно 30: разработка и небольшая validation-часть. Группу X-4/X-47 с неоднозначной отметкой оставить в train/dev для совместного разбора. Ответственный за ML не получает ролики и эталонные ответы закрытой части. Если после просмотра обнаружены дополнительные похожие сцены, объединить группы без переноса уже использованных сцен в независимый test. Если все ролики уже использованы при выборе модели или промптов, такую оценку честно назвать development; для независимой проверки снять новые примеры.

За первые 45–60 минут Омар просматривает train/dev, Анияр отдельно проверяет закрытую часть и при возможности помогает с train/dev. Так весь уникальный материал проверяется командой без передачи закрытых сцен ML-направлению. Для положительного примера: наблюдаемый факт, начало/конец, конкретный тип, видимость, возможный источник; для отрицательного — похожее допустимое действие, способное вызвать ложное срабатывание. Это бюджет команды, не измеренное время аннотирования. Спорные группы train/dev, прежде всего X-4/X-47, проверить обоим участникам. Таксономию и промпты выбирать только по train/dev и публичным нормам.

## Нормативы и неизвестные условия

Найдены кандидаты из Правил НБРК № 231 от 29.11.2019; конкретные основания и границы применимости — в `docs/normative_candidates.md`. Предварительно полезны пункты о завершении обслуживания, пересчёте при клиенте, хранении ранее принятой наличности и приёме инкассаторских сумок. Это направления проверки, не установленная таксономия роликов. Текущую консолидированную редакцию нужно сверить в «Әділет»; не допускать кандидата в итоговую систему до проверки.

У организаторов стоит уточнить одним сообщением, которое отправит капитан:

- Канал и точный формат сдачи URL/API-ключа; одновременность запросов жюри и момент старта 300 секунд.
- X-4 и X-47 имеют одинаковое содержимое и отметки 57/68: два события или альтернативная разметка?
- Допускаются ли дополнительные поля JSON для нормативной ссылки? До ответа ссылка остаётся в description.
- Как оценивать корректно обработанное, но неразборчивое видео: FAQ упоминает недостаточность данных, хотя схема допускает только два вердикта?
- Что именно считается запрещённым «готовым решением» из FAQ 35, учитывая разрешение предобученных моделей и кода в FAQ 24?

Эти вопросы не блокируют базовую реализацию по строгой схеме. Пользовательские ответы уже учтены: цель 21:00 сегодня; RTX 3060 6 ГБ у Анияра; RTX 3050 4 ГБ и сервер сервер у Омара; раздельные компьютеры и Git-ветки.
