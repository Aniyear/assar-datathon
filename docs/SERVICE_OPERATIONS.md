## Короткие команды

В PowerShell из интеграционного checkout:

```powershell
Set-Location 'C:\Users\aniya\Рабочий стол\assar-datathon\.worktrees\integration-cpu'
# Проверка без загрузки модели; текущая сборка честно выдаёт НЕ ГОТОВО.
.\scripts\assar.ps1 check --runtime-root '..\ml-portability-3060'

# Только после принятого ML-handoff, проверки правил/readiness и согласования GPU:
.\scripts\assar.ps1 start --runtime-root '..\ml-portability-3060' --port 8000
# В другом терминале, либо Ctrl+C в терминале запуска:
.\scripts\assar.ps1 status
.\scripts\assar.ps1 stop
```

`start` работает в текущем терминале; не закрывать его во время работы сервиса.
Скрипт выбирает `.venv` checkout или существующий общий `../../.venv`; не устанавливает
зависимости и не скачивает веса. На новой машине нужны CPython 3.11,
`python -m venv .venv`, `.venv\Scripts\python.exe -m pip install -r requirements.lock`,
FFmpeg/ffprobe в PATH и подготовленные runtime/веса. Прямая эквивалентная команда:
`python -X utf8 -m scripts.service check|start|status|stop` с теми же параметрами.

`--runtime-root` — фактическая база относительных путей GGUF/mmproj/llama-server.
На этой машине проверена папка `.worktrees/ml-portability-3060`, а не `../..`.
Другой handoff может требовать другой папки. `--model-config` принимает конфиг
кандидата; путь разрешается относительно текущей папки. Launcher меняет только
три пути файлов в локальной копии `outputs/service/production/resolved-model.json`.
Исходный конфиг, параметры, status и validation сохраняются. В production по-прежнему
выполняется штатный `production_spec`; тестовый каталог туда не подставляется.

Проверяются версии из lock, FFmpeg/ffprobe, SHA256 runtime/весов/mmproj,
каталог, readiness и видимые `nvidia-smi` вычислительные процессы. При конфликте GPU
запуск отклоняется, чужие процессы не останавливаются. Пустой список PID не заменяет
согласование слота с Омаром. Preflight не является измерением качества или GPU-инференса.

## Ключи, результаты и остановка

- Случайные ключи production и network-test раздельны. Файл:
  `outputs/service/<mode>/private/api-key.txt`; директория ограничена Windows ACL
  текущего пользователя (на POSIX 0700). Значение не печатается и не попадает в argv,
  URL, клиентский JS, Git или access-log. Каталог `outputs` целиком ignored.
- Для ввода в собственный браузер можно локально скопировать ключ:
  `Set-Clipboard -Value (Get-Content -Raw outputs/service/production/private/api-key.txt)`.
  Вставить в поле ключа, после использования очистить буфер. Не отправлять ключ в чат.
- Production использует `outputs/service/production/results/jobs.sqlite3` и отдельный
  uploads-каталог. Результаты сохраняются после штатной остановки. Не перемещать старую
  базу в новый путь молча. Резервную копию делать после `stop` либо SQLite backup API.
- Один launcher на режим защищён файловой блокировкой. `stop` записывает запрос
  **конкретному run_id**, не посылает сигнал PID из файла. Uvicorn завершает lifespan,
  supervisor останавливает свои worker/model/decoder. Тестовый tunnel — в отдельном
  принадлежащем launcher Job Object, завершается при остановке/смерти владельца.
- Повторный `stop` безопасен. При неподтверждённой остановке за 60 секунд команда
  сообщает ошибку, не выполняет taskkill по имени/порту. Состояние и итог каждого
  запуска: `state.json` и `run-<run_id>.json` в каталоге режима. `status` показывает
  свежесть heartbeat; устаревший heartbeat не считать работающим сервисом.
- Не запускать с `--reload`, несколькими Uvicorn workers или открытым портом модели.
  Launcher слушает только `127.0.0.1`.

## Воспроизводимый внешний тест без банковских данных

Проверен также [ngrok с постоянным бесплатным адресом](NGROK_TEST.md): два запуска,
32/32 HTTP-проверки, тот же URL после перезапуска и отдельное подтверждение
мобильного доступа. Ниже сохранён ранее проверенный вариант Cloudflare со сменным URL.

```powershell
# Один раз; уже скачано на этой машине. Проверяет закреплённый SHA256.
.\scripts\install-network-tool.ps1
.\scripts\assar.ps1 start --mode network-test --port 18766 --tunnel outputs/tools/cloudflared-2026.10.1.exe
# Другой терминал:
& '..\..\.venv\Scripts\python.exe' -m scripts.validation.network_check
.\scripts\assar.ps1 status --mode network-test
.\scripts\assar.ps1 stop --mode network-test
```

В терминале появится новый HTTPS-адрес. Нужен исходящий интернет, но аккаунт,
домен, покупка сервера и открытие входящих портов для этого теста не нужны.
Тестовый сервер имеет только страницу, `/health` и защищённый `/api/test`.
Любой POST/PUT и загрузка отклоняются **до чтения тела**. Производственного API,
inference, доступа к данным/каталогу, модели и файлового сервера здесь нет.
Страница явно помечена «ТЕСТ СЕТИ». Правильный ключ проверяется только тестовым API.

Использован официальный cloudflared **2026.10.1**, Windows amd64, 55 325 120 байт,
SHA256 `4d2490e74082c5d48dbfedaf92576fa5bd1702379ab88eb7faa0cfbe8dc891b6`.
Хеш сверён с digest [официального GitHub release](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.1).
Скачанный бинарник и квитанция находятся только в `outputs/tools`.
[Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
предназначен для тестирования: URL меняется при запуске, гарантии доступности нет.
HTTPS проверяется штатно, редиректы с ключом запрещены. Access-log выключен.

Для другой сети: отключить Wi-Fi на телефоне, открыть **новый** URL через мобильный
интернет и увидеть «ТЕСТ СЕТИ». Ключ для проверки страницы не нужен. Автопроверка
с ноутбука через публичный URL и человеческое подтверждение мобильной сети —
разные свидетельства, записываются раздельно.

Тестовый туннель не является каналом передачи банковских видео жюри: HTTPS
заканчивается также на инфраструктуре Cloudflare. Кнопка `--tunnel` намеренно
недоступна для production. Для сдаваемого доступа нужен согласованный канал команды.
Если выбирается прямой HTTPS/reverse proxy из MVP_LAUNCH.md, конкретный вход от
команды — управляемый публичный сервер/IP и право настроить DNS/порты. Сейчас их нет.
Для Cloudflare-теста вход в аккаунт не требовался. Позже пользователь создал
бесплатный аккаунт ngrok и выполнил официальную настройку; [его тест](NGROK_TEST.md)
не означает публикацию production или одобрение канала для банковских материалов.

## Приём ML и финальный запуск на 3060

1. Омар передаёт **точный commit/base**, выбранную модель, SHA256/runtime/параметры,
   метод оценки, агрегаты, реализованные условия правил и контрпримеры, предлагаемые
   изменения общих файлов и известные ошибки. A/B-разметка пользователем не требуется.
2. `git fetch origin`, `git show --stat <handoff>`, проверить diff от принятого
   `5c61ccc3ef8976ba38d1cbc63f056516c46216fe`. Не вливать всю `origin/codex/ml`
   автоматически; проверить общий контракт и точные импорты, затем принять согласованный diff.
   Внешний интерфейс сохраняется: `analyze_video(video_path: Path, job_dir: Path,
   deadline_monotonic: float) -> AnalysisResult`. Factory получает `call_timeout_sec`.
3. Внести только обоснованные общие настройки/правила. Проверки условий и applicability
   обязательны для verified; не изменять все validation-флаги ради запуска.
   CPU-проверки — затронутые новым diff; финальный общий suite один раз на кандидате.
4. Согласовать завершение процесса Омара на 3060, выполнить `assar.ps1 check`
   с фактической папкой новых весов. Ошибка проверки — конкретный блокер, не повод
   отключить проверку. Закрепить конфиг/каталог/веса и code commit для квитанции.
5. Если новая связка требует технического измерения до production readiness,
   использовать существующий `scripts/validation/gpu_smoke.py --run-gpu
   --runtime-root <проверенная-папка> --call-timeout-sec 17` **только после согласования GPU**.
   Этот стенд читает текущий configs/model.yaml и отдельный синтетический каталог;
   проверить совместимость его категории с новым ML. Если несовместим — сначала
   адаптировать синтетический стенд к handoff, не подделывать PASS и не менять production.
6. После фактического подтверждения условий готовности — обычный `assar.ps1 start`
   и один проход [MVP_ACCEPTANCE.md](MVP_ACCEPTANCE.md): реальные положительный/
   отрицательный dev, done/JPEG, полный upload→terminal ≤300 с, повтор, сохранение
   после очистки и перезапуска. Содержимое и смысл проверяются локально командой.
7. Внешняя проверка финального API с ключом и реальными данными — только через
   согласованный канал. Тестовая страница и её ключ не передаются как продукт жюри.

Неполученные входы остаются блокерами: финальный handoff Омара, применимые правила,
готовность новой конфигурации по измерениям и сдаваемый канал доступа. Старый smoke
или успешная сеть не заменяют ни один из этих входов.
