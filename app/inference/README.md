# ML inference (codex/ml): baseline без обучения

Qwen3-VL-2B-Instruct (GGUF) исполняется локальным `llama-server` из llama.cpp. Сервер слушает только
`127.0.0.1` и запускается с `--offline`. FFmpeg декодирует видео; время каждого кадра — фактический PTS
из фильтра `showinfo`, rotation metadata применяется autorotate FFmpeg. Обучение не выполнялось.
`analyze_video` реализован по общему контракту 0.1 (`app/contracts.py`, bootstrap `5c748f9`) и подключается
к backend через `app.inference.service`, см. разделы «Интеграция с backend» и «Условия вердикта». **Production заблокирован**, пока в `app/rules/catalog.json` нет verified-правил.

## CUDA: драйвер, runtime DLL и Toolkit — разные вещи

- **Драйвер NVIDIA** даёт только поддержку CUDA API (`nvidia-smi` показывает максимальную версию). Сборке
  CUDA 12.4 по таблице NVIDIA нужен драйвер ≥ 551.61 для Windows. Проверено на драйвере 565.90.
- **CUDA runtime DLL** (`cudart64_12.dll`, `cublas64_12.dll`, `cublasLt64_12.dll`) драйвер не устанавливает.
  Без них `ggml-cuda.dll` не загрузится, и llama.cpp не сможет использовать GPU. Эти DLL берутся из архива
  `cudart-llama-bin-win-cuda-12.4-x64.zip`; `fetch_runtime.py` распаковывает его в тот же каталог, что и `llama-server.exe`.
- **CUDA Toolkit** ставить не нужно. На машине рабочего запуска Toolkit не установлен, `CUDA_PATH` не задан.
  Если Toolkit другой версии стоит в `PATH`, DLL из каталога `llama-server.exe` всё равно грузятся первыми.

## Интеграция с backend (worker и supervisor)

Backend (`codex/backend` @ `1a3bda0`, `app/jobs/ML_INTERFACE.md`) импортирует модуль
`app.inference.service` — тонкий адаптер над `config.py`, `vlm.py` и `analyzer.py`:

```python
from app.inference.service import check_runtime, create_analyzer, server_command
```

| Функция | Где вызывается | Что делает | Ошибка |
|---|---|---|---|
| `check_runtime(model_cfg, repo_root)` | API, один раз при старте | Размер и SHA256 весов и mmproj, наличие и SHA256 `llama-server.exe` (`runtime.server_sha256_reported`); проверка закреплённых флагов. Без процессов и сети | `ModelUnavailableError` |
| `server_command(model_cfg, repo_root, port)` | supervisor перед `Popen` | Чистая функция: argv с `--host 127.0.0.1 --port <port> -c 8192 -ngl 99 -np 1 --no-webui --offline --jinja --image-max-tokens 256` и абсолютными путями от `repo_root` | `ModelUnavailableError` (порт вне 1–65535, config без `--offline`/`-np 1`/…) |
| `create_analyzer(endpoint, model_cfg, catalog, repo_root, call_timeout_sec=120.0)` | worker, один раз после health | Клиент `endpoint` (только `http://127.0.0.1:<port>`, без proxy и редиректов), `Analyzer`, проверка `/health` ≤ 2 с. `call_timeout_sec` = `Settings.model_call_timeout_sec`: предел одного запроса, дополнительно ограниченный остатком deadline. Возвращает `analyze_video` | `AnalyzerNotReadyError` (нет verified-правил, type_id вне категорий промпта, версия промпта), `ModelUnavailableError` (в т. ч. `call_timeout_sec` не конечное положительное число) |

Процессы модели запускает и останавливает только supervisor; адаптер не создаёт второй сервер.
`ffmpeg`/`ffprobe` запускаются обычным `subprocess.run` (`CREATE_NO_WINDOW`, без breakaway/detached)
и наследуют Job Object worker'а. Socket timeout запроса к модели ≤ остатка deadline, но генерацию на GPU
не прерывает — это делает watchdog supervisor'а.

**Ошибки `analyze_video`** — только наследники `AnalysisError`, сообщения без путей и ответов модели:

| Ситуация | Тип | Supervisor |
|---|---|---|
| Путь видео не абсолютный / файла нет, ffprobe/ffmpeg не прочитали, PTS вне длительности | `DecodeError` | мягкий: сервер переиспользуется |
| Все окна непригодны; часть окон непригодна и verified-событий нет; verified-событий нет, но есть `other_notable_action` | `UnassessableVideoError` | мягкий |
| Ответ обрезан / не JSON / неверный индекс кадра / пустое или пробельное описание наблюдения; наблюдения кандидатных категорий без verified-правила при отсутствии событий; результат не прошёл общие валидаторы | `InvalidAnalysisResultError` | мягкий |
| HTTP-ошибка, недоступность llama-server | `ModelUnavailableError` | перезапуск |
| Исчерпан deadline, timeout ffprobe/ffmpeg/запроса | `AnalysisTimeoutError` | перезапуск |
| `job_dir` не абсолютный/не существует, deadline не конечное число, любой непредвиденный сбой | базовый `AnalysisError` (причина в `__cause__`) | перезапуск |

Для `job_dir` и deadline подходящего наследника в контракте нет — это ошибки вызывающей стороны;
базовый `AnalysisError` означает жёсткий сбой (вопрос интегратору).

## Условия вердикта

Модель по каждому окну возвращает `frames_assessable` и наблюдения с категорией из `prompts.CATEGORIES`.
Совпадение категории с `type_id` verified-правила — **единственная** программная связь с правилом:
`required_context` и `counterexamples` каталога — текст, машинно не проверяются; это отражено в
`limitations` каждого результата и должно учитываться при переводе правила в `verified`.

1. Любое окно с невалидным/обрезанным ответом → `InvalidAnalysisResultError` (job failed).
2. Все окна `frames_assessable=false` → `UnassessableVideoError`.
3. Есть наблюдение категории verified-правила → событие(я) → **`violation`** (непригодные окна и
   наблюдения без правила остаются в `limitations`).
4. Событий нет:
   - есть наблюдения кандидатных категорий без verified-правила → `InvalidAnalysisResultError`;
   - есть непригодные окна → `UnassessableVideoError`;
   - есть наблюдения `other_notable_action` → `UnassessableVideoError` (политика MVP, B6: такое действие
     не признаётся нарушением, но и не доказывает его отсутствие);
   - иначе (все окна пригодны и наблюдений нет совсем) → **`no_violation`**.

Пустое или пробельное описание любого наблюдения → `InvalidAnalysisResultError` (B5): `observed_fact`
события — только текст модели, общий текст вместо него не подставляется.

**Следствие политики:** консервативные правила 2 и 4 (непригодные окна, кандидатные категории без
правила, `other_notable_action`) переводят неопределённые случаи в `failed` вместо `no_violation`.
Доля `failed` может заметно вырасти; насколько — не измерено (зависит от того, как часто модель
выдаёт такие категории на реальных роликах).

Пустой каталог блокирует старт (`AnalyzerNotReadyError`), а не выдаёт `no_violation`. Порогов на число
кадров/длительность события нет: их нужно задавать вместе с verified-правилом, а не подбирать.

## Длительность и VFR (B8)

Время кадра — PTS из `showinfo`; граница — длительность контейнера `format.duration`, та же, что
проверяет backend (`app/jobs/media.py`). В MOV с переменным FPS **и B-frames** edit list, который
пишет mov-muxer, оказывается короче последних декодируемых кадров. Синтетический fixture
(0–2 с при 30 FPS, далее шаг 0,1 с, x264 по умолчанию, `has_b_frames=2`):

| FFmpeg (кодирование и проба) | duration контейнера | последний декодированный PTS | с `-bf 0` |
|---|---:|---:|---:|
| 7.1.1 essentials (gyan.dev) | 7,767 | 7,8 | duration 7,9 ≥ PTS |
| N-122607 (BtbN, 31.01.2026) | 7,8 | 7,9 | duration 7,933 ≥ PTS |
| N-123073 (BtbN, 28.02.2026) | 7,8 | 7,9 | duration 7,933 ≥ PTS |

Сборка интегратора N-122697 (10.02.2026) лежит между двумя проверенными; по данным интегратора на ней те же 7,8/7,9. Саму N-122697 я не запускал: в архиве BtbN её нет.
Причина — источник длительности, а не вычисление времени: PTS кадров реальны, но по edit list
хвост после `duration` не входит в представленный ролик (плеер и backend его не учитывают).
Fixture корректен как пример такого файла. Исправление: декодирование только диапазона
`[0, duration)` (`-t duration` на входе FFmpeg); clamp не применяется, PTS вне диапазона
по-прежнему `DecodeError`. Кадр с PTS ровно `duration` тоже не берётся: его показ начинается в конце
ролика. Ограничение: если контейнерная длительность сама неверна (существенно короче содержимого),
хвост будет молча исключён; отдельной проверки на это нет.

одной сборке и одном видео. На RTX 3060, другом драйвере или другой сборке llama.cpp результат может
отличаться; это нужно проверить тем же сравнением хешей.

**Без успеха на RTX 3050 4 ГБ:** mmproj F16 без `--image-max-tokens` (~420 токенов на кадр, `--ctx` 16384 и 8192)
— после нескольких окон `llama-server` падает с `bad allocation`; при `--max-tokens 160` ответы обрезаются.

## Ограничения

- На целевой RTX 3060 Laptop 6 ГБ не измерено.
- Самое длинное видео не измерялось.
- Качество наблюдений и локализации не оценивалось.
- `--image-max-tokens 256` снижает детализацию мелких объектов. llama.cpp предупреждает, что для grounding
  Qwen-VL нужно ≥ 1024 токенов на изображение.
- Выборка 1 кадр/с может пропустить короткие действия.
- Категории промпта предварительные, до таксономии v1.

## Режим CASH-01: факты и условия (`cash01-facts-v1`)

Включается версией промпта в config: `generation.prompt_version = "cash01-facts-v1"`, `generation.max_tokens = 512`
(запись в `configs/model.yaml` делает интегратор). По умолчанию остаётся `obs-v0.1`.

- Модель по **каждому кадру** отвечает `yes / no / unknown`: кассир на рабочем месте, клиент у кассы,
  видимое обслуживание (`facts_prompt.py`). Вывода о нарушении модель не делает.
- Условия п. 22 Правил № 231 проверяет код (`conditions.py`) по всей временной линии, через границы окон:
  отсутствие кассира ≥ 3 кадров подряд; клиент у кассы на каждом кадре отсутствия; обслуживание видно
  до ухода и после возвращения (≤ 15 с), клиент у кассы непрерывно.
- Контрпримеры (клиент тоже ушёл, нет видимого обслуживания до/после, отсутствие короче 3 кадров) не дают
  событие. `unknown` в проверяемом интервале или отсутствие, обрезанное началом/концом видео, при отсутствии
  событий → `UnassessableVideoError` (failed), не `no_violation`.
- Событие: `timecode_sec` — первый кадр отсутствия; 3 реальных JPEG (обслуживание до, середина отсутствия,
  обслуживание после); `observed_fact` собирается из фактов с временами кадров.
- Нужен ровно один verified-правило с `type_id = "cashier_leaves_during_service"`; иначе `AnalyzerNotReadyError`.
- Покрытие — только CASH-01; другие типы нарушений не анализируются (их положительные видео будут FN).
- Роль кассира задаётся контекстом задачи (сотрудник со стороны кассы), личность не устанавливается.

## Режим cash-events-v4 и итоги dev (финальный кандидат)

| Тип | Условие | Норма (Правила № 231) | Статус |
|---|---|---|---|
| ACCESS-01 | Посторонний на стороне сотрудника / у сейфа ≥ 4 кадров подряд (порог подобран на train) | пп. 75, 76 | включён |
| CASH-01 | Кассира нет ≥ 3 кадров, клиент у кассы | п. 22 | включён, на dev событий нет |
| CASH-02 | Пересчёт ≥ 2 кадров без клиента, клиент был незадолго до этого | п. 20 абз. 1 | включён, на dev событий нет |
| SAFE-01 | Кассира нет, сейф открыт / ключ оставлен | пп. 20 абз. 2, 80 | **выключен**: не распознаётся |

Failed — только если модель не может судить о присутствии кассира почти на всех кадрах (FAQ 15).

Итог, модель 4B Q4_K_M, `cash-events-v4`, max_tokens 900 (одна машина с GPU уровня сервера; скорость на
RTX 3060 нужно измерить отдельно):

| Набор | Найдено положительных | Ложные срабатывания | Верные вердикты | Failed | Время на видео |
|---|---|---|---|---:|---|
| train (12 / 10) | 1 / 12 | 1 / 10 | 10 / 22 | 0 | 11,2 с ср., 30,4 с макс. |
| dev (4 / 4) | 1 / 4 | 0 / 4 | 5 / 8 | 0 | 12,1 с ср., 28,5 с макс. |

Сравнение на тех же видео: 2B не видит пересчёт/сумку/сейф; Qwen3.8-27B (не помещается в 3060) — тоже не
распознаёт сейф/ключи/пересчёт надёжно; на ACCESS-01 даёт похожий результат. Это диагностика на 30 видео, не
оценка устойчивости. Соответствие найденного события реальному типу нарушения подтверждает человек (метки
бинарные, без типа). Frozen test не использовался.

Известные ограничения: большинство нарушений в данных (сейф/ключи, смешение денег, пересчёт) моделью не
распознаётся; ACCESS-01 даёт ложные срабатывания, когда рядом с кассиром нормальный посетитель/коллега;
полномочия людей по видео не устанавливаются.

## Финальный кандидат v6 (`cash-specialists-v6`)

Типы выбраны по парам «нарушение / эталон» в train/dev. Два «специалиста» — отдельные короткие запросы на окно:
«люди» (кассир в комнате; сколько людей кроме кассира внутри: 0/1/2+) и «стол» (деньги, монеты или мешок на
столе). Условия проверяет `rules_v6.py`; кандидат MULTI-01 дополнительно подтверждается узким запросом по трём
кадрам (`facts_v6.VERIFY_MULTI`): событие остаётся, только если подтверждены все три.

| Тип | Условие | Норма | Статус |
|---|---|---|---|
| MULTI-01 | ≥ 2 человек кроме кассира внутри комнаты ≥ 2 кадров, кассир на месте, проверка 3/3 | п. 20 абз. 2 | включён |
| CASH-03 | кассира нет ≥ 3 кадров, ценности на столе ≥ 2 кадров отсутствия | п. 20 абз. 2 | включён, на train/dev событий не дал |

Итог 4B Q4_K_M, 256 визуальных токенов на кадр, max_tokens 500 (скорость на RTX 3060 измерить отдельно):

| Набор | Найдено | Ложных | Failed | Время на видео |
|---|---|---|---|---|
| train (12 / 10) | 1 / 12 | 1 / 10 | 0 | 14,2 с ср., 38,1 с макс. |
| dev (4 / 4) | 2 / 4 | 0 / 4 | 0 | 15,1 с ср., 36,0 с макс. |

Верных бинарных вердиктов 16 из 30 (у v4 и v5 — 15 из 30). На X-18 тип совпадает с нарушением по разбору
(одновременно два клиента). Модель не распознаёт ценности на столе, уход кассира, сейф и ключи, пересчёт и
детектор подлинности — это основные ограничения. Frozen test в настройке не использовался; разбор, где он
описан, получен вне этого потока, поэтому test нельзя считать независимой проверкой.


## v6: дедлайн, перепроверка, рамки и инструменты оценки

- **Укладка в дедлайн** (`analyzer._Budget`): после первого запроса замеряется цена кадра; если все проходы
  не успеть до дедлайна backend (с запасом на проверки и сборку), с текущего окна пропускается «стол»
  (CASH-03 там не оценивается), затем берётся каждый 2-й/3-й кадр. Всё это пишется в limitations и в trace (`budget`).
- **Плотная перепроверка MULTI-01** (`_dense_multi`, выключена `DENSE_CHECK = False`: на train+dev в core теряет 2 TP ради 1 FP): до 10 кадров через полшага у начала кандидата
  (`video.sample_range`, сдвинуты относительно основной выборки), тот же вопрос «люди». Пока только запись в
  trace (`dense`); `MULTI_DENSE_IN_CORE = True` делает её обязательной — включать по замеру `report.py` (раздел dense).
- **Рамки** (`ANNOTATE_EVIDENCE`): на среднем доказательном кадре MULTI-01 модель даёт рамки людей кроме кассира
  (сетка 0–1000), ffmpeg рисует их на копии кадра. Меньше двух рамок или любой сбой — исходный кадр.
- `experiments/augment.py` — копии видео с другой геометрией (зеркало, кадрирование, поворот, перспектива).
- `experiments/report.py` — метрики отдельно по train и dev, разбор пропусков «тип не покрыт / не распознан»
  (локальный `types.local.csv`), устойчивость к ракурсу, «что если» для перепроверки, подбор порогов по trace (`--tune`).
- `experiments/absence_cv.py` — отсутствие кассира по движению в автоматически найденной зоне (без нейросети).

### Замер v6 (4B Q4_K_M, train 22 + dev 8 + 32 копии dev)

| Набор | TP | FN | FP | TN | Recall | Precision |
|---|---|---|---|---|---|---|
| train | 1 | 11 | 1 | 9 | 8% | 50% |
| dev (без копии X-4) | 1 | 2 | 0 | 4 | 33% | 100% |
| всего | 3 | 13 | 1 | 13 | 19% | 75% |

- Пропуски (13): 10 — тип нарушения не покрыт двумя правилами (ключ в сейфе, двери, ноутбук, напитки и др.),
  3 — тип покрыт (ценности на столе), но не распознан; 2 нарушения найдены под другим типом.
  Из 16 положительных к поддерживаемым типам относятся 4.
- Ракурс (копии dev): ложных 0/16 на всех искажениях; совпадение вердикта с исходным — поворот 8/8,
  кадрирование 7/8, перспектива 6/8, зеркало 5/8; полнота нестабильна (перспектива 0/4).

- `absence_cv`: «уход» чаще на эталонах (6/10), чем на нарушениях (3/12), с ответами модели не совпадает — не используется.
