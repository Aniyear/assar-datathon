## Границы данных и вывода

- Видео, кадры, их описания, аннотации наблюдений и результаты распознавания остаются на локальной машине команды. Не отправлять их в облачные AI-сервисы, инструменты просмотра изображений облачной модели или внешнюю телеметрию. Код, технические метаданные без содержимого сцен, агрегированные метрики и открытые нормативные источники можно обсуждать с агентами.
- data/, analysis/local/, models/, weights/, uploads/, outputs/ и секреты исключены из Git. Не прикреплять датасет к PR, issue или облачному чату. Тестовые видео жюри не использовать для обучения.
- Анализ только визуальный; не использовать звук, распознавание или идентификацию лиц.
- Runtime после загрузки зависимостей и весов работает без внешнего доступа. API локальной модели в собственном процессе/на localhost допустим как технический интерфейс; внешний inference provider не допустим.
- Не выдумывать наблюдения, юридические основания, метрики, результаты тестов. Нечитаемый кадр не доказывает отсутствие обязательного действия.
- Ошибка модели или декодирования — failed, а не no_violation. Внешний вердикт только violation/no_violation. Моки не должны попасть в сдаваемый режим.

## Совместная работа

- По решению пользователя от 17.10.2026 один Codex у Анияра отвечает за весь программный продукт: app/web/**, app/api/**, app/jobs/**, tests/api/**, интеграционные проверки, запуск, deployment и общие файлы. Основная сборка и рабочий checkout — codex/integration-cpu. Отдельные frontend/backend/GPU-чаты больше не являются параллельными владельцами этих файлов.
- Омар с одним ML-Claude владеет app/inference/** и tests/inference/** в codex/ml; определяет модель, качество, наблюдаемые условия и применимость правил. Готовые изменения принимаются по точному handoff, а не по новизне ветки. Капитан Омар выполняет отправку жюри. Распределение и карта сохранённых веток — docs/BRANCH_MAP.md; финальный план — docs/01_CURRENT_STATE_AND_FINISH_PLAN.md.
- Единственная параллельная активная ветка — codex/ml. Старые ветки, worktree и локальные файлы сохранять. Не выполнять reset, clean, force-push и переключения чужих checkout. Новые рабочие ветки создавать только при конкретной необходимости. main обновляется проверенной сборкой при фиксации релиза.
- Один пишущий агент на отдельную ветку И отдельный checkout/worktree. Не запускать параллельные git switch/reset/clean в общей папке. Не отменять чужие изменения.
- Владение файлами закреплено в docs/IMPLEMENTATION_PLAN.md. Изменения чужого интерфейса сначала предложить интегратору с причиной и влиянием; не менять контракт в своей ветке молча.
- docs/CONTRACTS.md и app/contracts.py имеют одного владельца — интегратора. Агенты работают по принятой версии; новая версия содержит миграцию потребителей.
- Зависимости и lock-файлы, configs/model.yaml, app/rules/catalog.json и deployment изменяет интегратор. Остальные сообщают необходимые дополнения в handoff.
- GPU занят только одним согласованным ML-процессом; остальные агенты работают с CPU/фикстурами. Не останавливать процессы пользователя для освобождения GPU.
- В handoff: задача, base commit, изменённые файлы, проверки с фактическими результатами, незакрытые риски, команды запуска, зависимости/изменения контракта. Подробные результаты видео сохранять локально, наружу выводить только агрегаты.
- Маленький интегрируемый результат каждые 60–90 минут. Никаких широких рефакторингов вне задачи. Каждый пакет имеет явные критерии готовности.

## Проверки перед интеграцией

Проверять контракт API, обработку ошибок, воспроизводимость и отсутствие утечки между группами видео; тесты по изменённому поведению. Зафиксировать версии модели, весов и зависимостей. Не считать работу модели подтверждённой до локального измерения. Публикация сервиса и отправка жюри — отдельные явно назначенные шаги команды; подготовка к ним не означает, что они уже выполнены.
